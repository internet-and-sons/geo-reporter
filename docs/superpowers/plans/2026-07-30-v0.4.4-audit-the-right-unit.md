# v0.4.4 — Audit the Right Unit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development. Steps use checkbox (`- [ ]`) syntax.

**Goal:** Fix the methodology gap a real client surfaced — the tool audited a section listing page as if it were the citable unit — plus the three false-signal bugs found during that same audit.

**Origin (read this, it justifies the whole release).** We delivered an audit of `zman.co.il/democracy`. The site owner replied that it wasn't helpful: that page is a **human navigation surface**, and the citable units are **the articles beneath it** plus **domain-level access**. He was right. Re-auditing the articles inverted the conclusions — the article template was already strong (single `<h1>`, `NewsArticle` schema, `dateModified`, unique per-article meta descriptions, full SSR) while the section-page report had recommended fixing H1s and descriptions that don't govern citation at all. The same audit run also produced two false signals we had to correct by hand before sending.

**Architecture.** Two halves. (1) **Right unit**: page-type classification + child-article sampling in `fetch_page.py`, exposed as a `section` mode, wired into `geo-audit` so a listing URL audits the articles beneath it and emits **canonical (template/domain-level) recommendations**. (2) **No false alarms**: fix the agentready 403 rule, the sameAs-liveness user-agent, and the `llmstxt_generator` challenge blind spot. All Python TDD.

**Tech Stack:** Python 3.8+ (requests, BeautifulSoup), pytest with `patch("<module>.requests.get")`.

**Baseline:** branch `fix/citability-challenge-fallback` at `3184f38`, **241 tests passing**. That branch carries an unmerged, unpushed fix (citability scorer challenge fallback) which rides along in this release — **base v0.4.4 on it, not on main.**

**Guiding rule for this release:** every false signal we ship costs client trust. Prefer "inconclusive / not measured" over a confident wrong answer, per report-contract rule 4.

Classification signals (evidence-based, not guesses):
- **article**: `structured_data` contains `Article`/`NewsArticle`/`BlogPosting`/`Report` → strongest signal; supported by exactly one `h1_tags` entry and a resolved `freshness.tier` (not `unknown`).

`confidence` ∈ `high` | `medium` | `low`; `signals` is a list of human-readable strings naming what fired ("no Article-family schema", "19 h1 elements", "38 article-shaped internal links"). The signals list is what the report quotes as Evidence, so write them for a reader.

Test cases: a real article shape (NewsArticle + 1 h1 + fresh) → `article`/high; the zman democracy shape (no Article schema + 19 h1 + unknown freshness + many numeric-path links) → `listing`/high; homepage path → `homepage`; an about page (1 h1, no Article schema, 3 internal links) → `other`; an ambiguous page (Article schema but 5 h1s) → `article` with lower confidence. ### Task 2: Child-article sampling + `section` mode

- [ ] **Step 1: Tests.** `sample_child_articles(page_data, limit=5, timeout=15) -> dict` returning:
```python
{"candidates": [...urls...], "sampled": [{"url","type","confidence"}...], "verified_count": int, "errors": [...]}
```
Behaviour:
- **Candidate extraction (no network):** from `internal_links` (entries are `{"url","text"}` dicts — handle both dict and bare-string forms defensively), keep same-host URLs that are *not* the page itself, and **exclude** obvious non-article paths: `/tag/`, `/tags/`, `/category/`, `/categories/`, `/author/`, `/writer/`, `/page/`, `/feed/`, `/about`, `/contact`, `/privacy`, `/terms`, `/search`, and anything ending in a file extension. Dedupe preserving order.
- **Spread the sample, don't take the first N** — take an evenly-spaced slice across the candidate list so the sample isn't all top-of-page featured items. (This is what a human analyst does.)
- **Verification (network, capped at `limit`):** fetch each sampled URL via `fetch_page` and run `classify_page_type`; keep those classified `article`. `verified_count` is how many confirmed. A URL that fails to fetch is recorded in `errors` and **excluded, never guessed at**.
- Deterministic ordering so a re-run samples the same URLs.

Tests mock `fetch_page.requests.get`. Cover: candidate filtering (nav paths excluded), even spread (given 40 candidates and limit 5, the picks are spread not the first 5), verification keeps only articles, a failed fetch lands in `errors` and not in `sampled`, empty candidates → empty result with no crash.

- [ ] **Step 2:** Add CLI mode `section`: fetch the URL, classify it, and if `listing` also sample children; emit `{"url","classification","sample"}`. If the URL classifies as `article`, say so and return the classification without sampling — the caller asked about the wrong unit and should be told, not silently redirected.

### Task 3: Fix the three false signals

**Files:** Modify `scripts/fetch_page.py`, `scripts/brand_scanner.py`, `scripts/llmstxt_generator.py`; Create `tests/test_false_signals.py`.

Each of these produced a wrong statement in a real client report. Fix all three; tests must prove the *false* case is gone, not just that the happy path works.

- [ ] **(a) agentready `endpoint` rule counts a WAF 403 as "found".** On a Cloudflare-strict site every path returns 403, so `/ask` and `/mcp` both registered as NLWeb endpoints existing. Change `found` semantics for `expects == "endpoint"`: `found` only when the status is a **2xx or 405** (405 = route exists but rejects GET, the real NLWeb signal). Add a third state so absence and blocked-ness are distinguishable: each check gains `"inconclusive": bool`, true when the status is 401/403/429 or the request errored. `summary` gains `inconclusive_count`. Same treatment for `json`/`text` checks: a 403 is inconclusive, not absent.

- [ ] **(b) `check_sameas_liveness` uses the spoofed Chrome UA**, so Wikimedia (policy T400119) 403s and Facebook 400s — reporting live profile links as broken. Use `WIKIMEDIA_HEADERS` for wikipedia.org/wikidata.org hosts (that constant already exists in the module from v0.4.0) and a descriptive UA elsewhere. Then add the honesty layer: a 401/403/429 result sets `"inconclusive": True` on the check and the URL is listed in a new `inconclusive` array rather than in `broken`. `broken` must mean *actually broken* (404/410/DNS failure), because that is what gets reported to a client as a defect.

- [ ] **(c) `llmstxt_generator.py` generate-mode page fetch (~line 164)** has the same WAF blind spot v0.4.3 fixed in `fetch_page` and the citability scorer. Apply the same guarded-import pattern the citability scorer now uses (`from fetch_page import AI_CRAWLERS, DEFAULT_HEADERS, is_challenge_page`, degrade gracefully on ImportError) and retry once with the GPTBot UA on a challenge.

- [ ] Tests in `tests/test_false_signals.py`: agentready with an all-403 host → `found_count == 0` and `inconclusive_count == 10`, and specifically `nlweb_ask["found"] is False`; agentready with a 405 on `/ask` → found True; sameAs against a 403-ing wikidata URL → `inconclusive`, NOT `broken`; sameAs against a genuine 404 → `broken`; sameAs wikimedia host gets the descriptive UA (assert on `call_args` headers); llmstxt generate-mode challenge → retries with GPTBot UA.

- [ ] Suite green → commit `fix: three false-signal bugs — WAF 403s no longer read as endpoints found or links broken`.

### Task 4: geo-audit unit-selection + canonical recommendations

**Files:** Modify `skills/geo-audit/SKILL.md`.

- [ ] **(a) Unit selection.** In Phase 1, after the ownership check, add:

```markdown
**Step 0b: Select the right unit to audit (mandatory).**

Run `fetch_page.py <url> section`. It classifies the URL and, for a listing, samples the articles beneath it.

- **`article`** → audit this page as given.
- **`listing`** (a section, tag, category, or feed page) → **the listing is not the citable unit.** It is a navigation surface built for humans; AI engines cite the articles beneath it. Audit the sampled child articles as the primary units, and treat the listing itself only as a discovery path (is it crawlable, does it link the articles). Say so in the report so the reader understands what was measured and why.
- **`homepage`** → audit as given, but sample a few articles too if the site is a publisher; a homepage is also mostly a navigation surface.
- **`other`** → audit as given.

**Never report listing-page cosmetics — H1 counts, meta descriptions, teaser word counts — as GEO findings.** They describe the wrapper, not the content anyone cites. A real site owner rejected exactly that report.
```

- [ ] **(b) Canonical recommendations.** Add to Phase 3, before the evaluator self-check:

```markdown
**Recommendations must be canonical.** When a finding recurs across sampled articles, it is a **template or domain-level** issue — write the fix at that level ("the article template's author node", "one Cloudflare rule") and state that it applies to every article at once. A per-page fix list for a template-level defect is unactionable at publisher scale. Say explicitly which layer each fix lands in: **domain / template / editorial habit**.
```
